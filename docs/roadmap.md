# 路线建议：定位与脚本语言决策

**本文是未立项的建议，不是承诺的排期。** 还没做的事在 `TODO.md`，已有的能力在 `README.md` 与 `docs/usage.md`，结构决策的理由在 `docs/architecture.md`。这里只放"为什么这样取舍"，供后续接手的人或 AI 查阅。

文中「已否决」一节是给未来的自己与接手者的防线——**不要重新提议那些方向**，除非定位本身变了。

## 1. 定位（决定一切取舍的那句话）

**竞争对手是开源工具（SavvyCAN / BUSMASTER / `candump`+PlotJuggler / `python-can`+cantools），不是 CANoe。**

目标是"比开源更流畅、更易用、功能更强，但保持轻"。由此推出竞争的四个维度：

1. 打开即分析（日志进来就能看、能统计）
2. 检索便捷（按 payload / 信号值 / 时间 / 地址过滤，能跳转、能标记）
3. 渲染不卡（大文件、大环、多窗口下的响应）
4. 零配置出结论（单文件工程，分享即复现）

反过来，CANoe 的"重"的来源**明确不做**——那些不是"更好的功能"，它们就是"重"本身，做了会稀释定位。清单在 `TODO.md` 的"边界外"一节。

**一个例外**：FlexRay 是用户 2026-09-19 显式重启的方向，不是逐步混入的。它当时被拿来论证"接收侧最多做到仅接收监听、不做信号解码"，实际按"FlexRay 要和 CAN 同一级支持"做完了接收侧与解码、观测、触发、录放、负载与规格，以及脚本的读侧；剩下的只有总线上的发送。这个例外的代价已经付掉了，别再引用旧结论。

保留的既有优势（别丢）：

- **DBC 解码的完整性**：复用报文、值表、浮点位模式。
- **数据来源纪律**：DBC 是拓扑的唯一数据来源 + 节点角色只管开关 + 驱动可插拔。这个概念上比 CANoe 干净，是产品论点的核心。
- **工程可复现**：`.rxproj` 单文件 + `profiles/*.toml` + 无头 CLI + `--check-script` 可进 CI。开源那一档基本没有，CANoe 那套又太重。

## 2. 三条曾经的主要差距，现在只剩一条

**日志进不来 / 检索不便 / 计量不够**——这是 2026-09-11 盘点时输给开源那一档的三处。检索与计量已经补齐（payload、信号值、时间范围、精确地址、游标、抖动、负载曲线、方向分离），日志侧则换了一条路：当初建议的"独立离线扫描通道"实现过又被删掉，因为回放加了 as-fast-as-possible 之后，"把整份日志一次读完"和"离线全量装载"是同一件事的两种叫法，两套入口只换来双份口径。

**仍然欠的是随机访问**：进度条只跟随不回跳，历史段不导出就回看不了。要不要做"常驻可回看的归档"，见 `TODO.md`。这一条是四维度里"打开即分析"唯一还没兑现的部分。

## 3. 脚本语言：保留自研，投资放在静态分析

**不引入 Lua 或任何通用语言底座。**

脚本的用途是刻意窄的（简单运算、应答、转发），而这条路线要的是**编译期判定**：编译时就能报出"发了不属于本节点的报文""到底应答了哪些报文"。这要求一门效果集合可静态推导的封闭语言，而通用脚本语言的便利**恰好来自让效果集合不可推导的机制**——id 可以从 table 里算出来、`load()` 能运行时造代码、metatable 能劫持名字解析。要保住可判定就得一条条禁掉，那时得到的是"阉割到只剩现有表达力的 Lua"，多一个引擎、一套沙箱、一堆限制规则，表达力一点没涨。纯赔。

反过来，**极简是可判定性的必要条件**，现有语言三条结构性事实正好支撑它：

1. 宿主函数表是编译期闭集，没有动态派发、没有 eval——效果面从语法树即可枚举。
2. 关键标识符全是字面量（定时器名、信号名、派生信号名），于是"哪个 handler 经哪个定时器回了哪个报文"这条响应映射可纯静态推导。通用语言里定时器名通常是变量，推导当场断掉。
3. 能产生 id 的出口只有字面量、常量算术、`frame_id()` 三处，而 `frame_id()` 的取值范围被 `on message <id>` / `on message *` 的事件绑定约束住——发送集有限可枚举。

FlexRay 的加入没有破坏这套东西，反而多了一条检查：`on fr slot` 处理器里 `frame_id()` 是槽号，所以 `send(frame_id())` 是编译错误——把槽号当 CAN id 发上 CAN 正是两套编号混用最典型的错。

**已生效的 fail-closed 规则**：`send` / `send_ext` 的第一个参数、`set_timer` / `emit_value` 的名字都必须静态可推导（字面量、字面量的常量算术、或 `frame_id()`），出现变量 id 一律**编译报错**，不留运行时回退。立这条规则等于永久拒绝"从文件或网络读 id"这一整类机制，这是该定位的应有代价，要在语言设计上明确接受。

这条路线已经走通了：编译期产出静态事实表（发送集及其所属处理器、接收集、响应映射、信号与系统变量引用、写死的信号值），装配层拿 DBC 交叉核对——拼错的名字、发了别节点的报文、`set_sig` 越出声明区间，都在启动时报出来，编辑器"收发"tab 打印同一份表，`--check-script --dbc` 复用同一路径做 CI 门禁。

`on message *` 的通配转发是推导不出发送集的那一种：编译器把这类发送单独记为"不可推导"并如实标注，而不是假装枚举完了。反向检查（DBC 声明本节点该发、脚本从不发）对通配脚本跳过——转发者/记录者本来就不该被要求发出库里每一条。

还可以加的一层（尚未做）：发送时对照编译期算好的发送集，越界就丢帧并记告警。编译期为主、运行时回退，两头都不静默。

可以加的表达力（不破坏可推导性）都已就位：`switch` / `case`、复合赋值、位运算符是纯语法糖，有界定长数组 `array(n)` 补上了最缺的"数组"——带界索引域分析起来毫无压力，这正是"嵌入式/安全关键 DSL"的标准做法。

一条判据：**每次给语言加特性前，先问"这会不会让效果集合变得不可静态推导"。**

外部仿真元件（电池模型、诊断栈、被控对象）是另一回事：它们要的是可扩展，与节点脚本要的可分析目标相反，该走进程内的注册缝，长期答案是有沙箱的多语言方案（WASM）。两件事不要混，也不要把裸 DLL 当答案（ABI 崩溃风险）。

## 4. 已否决的方向（不要重新提议）

| 方向 | 否决理由 |
| --- | --- |
| 换 Lua / JS / Python 作节点脚本底座 | 与"编译期可判定"正面冲突；得到的是表达力不变的阉割版 + 更多代码（见第 3 节） |
| 独立于回放的离线扫描通道 | 实现过、删了。与 as-fast-as-possible 是同一件事的两种入口，双份口径没有收益 |
| 面板设计器 / HMI 控件 | 属于 CANoe 的"重"，且需要一整套动态控件事件模型，现无 |
| 诊断栈（UDS / ODX / CDD / 刷写） | 边界外的独立产品面，不是"多一种总线" |
| 工业级测试报告（HTML / XML / PDF 模板） | 与"零配置出结论"冲突；CSV + CLI 退出码已够，判定框架另议（见下） |
| 多机分布式测量、实时系统、时间同步 | 定位外；核心线程是普通线程，空闲即休眠 |
| 用户 / 权限管理、国际化 | 当前受众不构成瓶颈；中文字体与输入法已解决实际痛点 |
| LIN / 以太网 / MF4 | 协议维度，按定位另行立项 |

**注意**：以上是"当前定位下"的否决。若定位改变（例如转向台架 / HIL 业务），面板与诊断需要重新评估——但那时也应是明确的重启决策，不允许逐步混入。

## 5. 待决策 / 需要举证的点

1. **id 的推导域要不要再放宽。** 现在算得出的只有：字面量、字面量之间的算术与位运算、`frame_id()`。对随仓库的九个示例跑一遍覆盖率：8 条发送全部可推导，零条例外——这批写法够用。要不要收静态全局的区间、循环变量的已知域，是另一个问题：放宽一档多一类写法，也多一片"看着能过检查其实没被枚举"的地带。真有脚本因此写不出来时，优先考虑加语法（常量表 / 枚举），而不是让推导变模糊。
2. **随机访问的语义与预算。** 可回看归档要不要做常驻浏览，大文件的装载时间与常驻内存目标是多少，与回放模式是不是同一个东西的两种驱动。**这是本建议里最需要先想清楚的设计问题。**
3. **发送集与 DBC 声明冲突时谁是权威。** 现在是一条启动告警、不拦发送。要不要升成编译错误、或允许显式豁免——网关 / 转发节点本来就要发送其他节点的报文，一律报错会挡住它们；建议默认更严 + 允许逐个豁免，但要明确选哪一种。
4. **判定框架的边界。** 从静态分析能自然长出一个门禁能力（"发送集符合 DBC 声明"作为一条断言）。要不要顺势做成"跑完仿真再给结论"的自动化测试单元，还是保持在 `--check-script` 的范围内。
