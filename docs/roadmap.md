# 路线建议：定位、优先级与脚本语言决策

**本文是未立项的建议，不是承诺的排期。** 已立项的工作项在 `TODO.md`；行为说明在 `README.md` / `docs/usage.md`；结构决策在 `docs/architecture.md`。本文只放"建议 + 依据 + 待决策"，供后续接手的人或 AI 查阅。

事实依据是 2026-09-11 对代码的一次只读盘点，每条结论都带 `文件:行号`，可直接复核；代码演进后行号会漂移，以符号名为准。文中「已否决」一节是给未来的自己与接手者的防线——**不要重新提议那些方向**，除非定位本身变了。

## 1. 定位（决定一切取舍的那句话）

**竞争对手是开源工具（SavvyCAN / BUSMASTER / `candump`+PlotJuggler / `python-can`+cantools），不是 CANoe。**

目标是"比开源更流畅、更易用、功能更强，但保持轻"。由此直接推出竞争的四个维度：

1. 打开即分析（日志进来就能全量看、全量统计）
2. 检索顺手（按 payload / 信号值 / 时间 / 标志位过滤，能跳转、能标记）
3. 渲染不卡（大文件、大环、多窗口下的响应）
4. 零配置出结论（单文件工程，分享即复现）

反过来，CANoe 的"重"的来源**明确不做**：面板设计器 / HMI、诊断栈（UDS / ODX / CDD / 刷写）、工业级测试报告、多机分布式测量、实时系统与时间同步（PTP / GPS）、多协议（LIN / FlexRay / 以太网 / MF4）、用户与权限管理。这些不是"更好的功能"，它们就是"重"本身；做了会稀释定位。

保留的既有优势（别丢）：

- **DBC 解码的完整性**：复用报文 `M`/`mN`/`mNM` + `SG_MUL_VAL_`、`VAL_` 值表、`SIG_VALTYPE_` 浮点位模式（`src/dbc.rs`）。
- **事实源纪律**：DBC 是拓扑唯一事实源 + 节点角色三态 + 驱动可插拔（`TODO.md` P0 / P4）。这个概念上比 CANoe 干净，是产品论点的核心。
- **工程可复现**：`.rxproj` 单文件 JSON + `profiles/*.toml` + 无头 CLI + `--check-script` 可进 CI。开源那一档基本没有，CANoe 那套又太重。

## 2. 现状与开源那一档的逐项对照

| 维度 | roxy-can 现状 | 开源那一档 | 判定 |
| --- | --- | --- | --- |
| 日志装载 | 必须按墙钟把回放跑完，Trace / 统计 / 规格 / 负载才有数据；`seek` 跳过的帧不补进任何聚合 | 直接整文件浏览（SavvyCAN / `candump` / `cantools`） | **落后** |
| 检索与过滤 | Trace 只有四项：总线范围 / Rx-Tx 方向 / DBC only / ID 或报文名子串（`src/workspace.rs:461-490`）；无 payload 字节搜索、无信号值过滤、无时间范围、无 Flags 过滤、无书签、无跳转时刻、无 reference trace 差异 | grep 级 payload 检索、hex 模式搜索、按条件过滤 | 落后 |
| 渲染规模 | Trace 渲染上限 1000 行（`src/ui/trace.rs:13`，环本身可到 2M）；曲线 8192 点 / 整窗 56000 顶点（`src/ui/graphics.rs:30,35`）；信号历史 1 小时（`src/app.rs:17`） | 规模有限但通常够用；大文件易卡 | 持平偏下 |
| 逐报文计量 | 无周期抖动 jitter、无位时间、无逐报文错误计数；`Avg` 是 EMA（α=0.1）非算术平均；聚合键不含方向导致收发计数合并、Dir 只反映最后一帧（`src/bus.rs:3078-3080`） | BUSMASTER 展示更全的逐报文统计 | 落后 |
| 总线级统计 | 有峰值负载、错误帧总数与速率；**无负载历史曲线**（`BusLoad::history()` 已实现但无人调用，`src/load.rs:350-360`）；无错误帧分类（form/stuff/CRC/ACK/bit）；Chip State 硬编码 "Simulated"（`src/ui/busstats.rs:9-12,149-156`） | 各有强弱 | 落后 |
| 离线分析 | **不存在离线模式**。帧入口只有回放源 `poll`；唯一真离线是 `--convert`（只转码不分析）。Graphics 的区间回填（`src/source/replay.rs:111-146`）是半个原型，但只填信号历史且受 30 万帧上限（`src/app.rs:28`） | 整文件即数据源 | **落后** |
| 观测窗口广度 | Graphics（多 Y 策略 / 分格 / 缩放平移 / 触发器 marker）、State Tracker（状态分段 + 自定义区间 + CSV）、Specification（四类判定，`src/spec.rs:25-34`） | 基本没有等价物 | **领先** |
| 工程可复现 | `.rxproj` + profiles + 无头 CLI + `--check-script` | 基本没有 | **领先** |
| 脚本可编程性 | 自研类 CAPL 语言，37 个内建（`src/script/mod.rs:239-279`），表达力窄但受控（10 万指令预算 + 熔断，`src/node.rs:18`） | SavvyCAN 内置 JS、`python-can` 直接写 Python | 持平（取向不同，见第 4 节） |

一句话：**这个工具输给开源的地方集中在"日志进不来 + 检索不顺手 + 计量不够"这三件事上，而它赢的地方（解码完整、观测窗口、工程可复现）全被第一件事卡住了**——日志进不来，再好的观测窗口也没有输入。

## 3. 优先级：离线分析优先

### 为什么是这一块

1. 它是**唯一比开源那一档还弱**的地方，而定位要求"比开源更强"，差距最大处即收益最大处。
2. 它**放大现有全部能力**：DBC 解码、Graphics、State Tracker、Specification 现在都只是"回放走到哪儿看到哪儿"，离线化之后才真正可用。
3. 它最符合"轻"：不碰硬件、不碰协议、不碰多机与实时，纯分析侧。
4. 它可演示：**"打开 1 GB BLF 秒开、全时间轴随便跳"是一句话能说清、且开源那一档做不到的差异**。

### 具体四件事（按此顺序）

1. **日志全量装载 + 真离线模式。** 让"文件即数据源"成为与回放并列的一条通道：不经回放时钟，把整段日志灌进聚合 / 统计 / 规格 / 采样缓存，所有观测窗口照常工作。现有资产：mmap 流式读 + BLF 解析（`src/log/blf.rs`、`memmap2`）、Graphics 区间回填（`src/source/replay.rs:111-146`，已是半个原型）。
2. **Trace 虚拟滚动，拆掉 1000 行上限。** `MAX_VISIBLE = 1_000`（`src/ui/trace.rs:13`）是渲染侧的自缚，环本身支持 2M。改成按可视区渲染（`TraceView` 已支持双向迭代，需确认能暴露元素总数以配合 ImGuiListClipper）。这是最容易被感知的流畅度改进。
3. **检索与过滤补到 grep 那一档。** payload 字节序列搜索、按信号值过滤、时间范围、Flags 过滤、书签与跳转时刻。当前 `trace_match` 只有四项（`src/workspace.rs:461-490`），这是"功能更强"最廉价的兑现。
4. **把已算出来但没上屏的计量补上（近乎零成本，优先做）。**
   - Data 窗口：订阅侧已累积 `min`/`max`/`avg`/`sum`/`n`/更新时刻（`src/observe.rs:291-319`），UI 一个都没显示。
   - 总线负载历史曲线：`BusLoad::history()`（100 ms 桶）实现完整，无人调用（`src/load.rs:350-360`，注释直言 sparkline 已被移除）。
   - 逐报文：周期抖动 jitter、收发方向分离统计（需改聚合键，`src/bus.rs:3078-3080`）。
   - 总线级：错误帧分类、控制器状态（接真实硬件后 Chip State 才有意义，仿真下保持标注）。

### 验收口径（与 `docs/architecture.md` 的开发约定一致）

判定逻辑用无头测试证明（离线装载后的统计/规格结果 == 同段回放的流式结果）；控件行为人工眼见（滚动、检索、跳转的响应）。

## 4. 脚本语言决策：保留自研，投资从"补表达力"转向"补静态分析"

### 结论

**不引入 Lua 或任何通用语言底座。保留现有自研语言，并把下一步投资放在编译期的效果静态分析上。**

### 判定依据

两个约束决定了这个结论：

1. 脚本的用途是**刻意窄**的：简单运算、应答、转发。
2. 路线图的核心是**编译期判定**，不是运行时判定：编译时就能报出"发了不属于本节点的报文""到底应答了哪些报文"。

这两个约束要求一门**效果集合可静态推导的封闭语言**。Lua（以及任何通用脚本语言）的便利**全部来自让效果集合不可静态推导的机制**，二者正面冲突：

- 报文 id 可来自 table、可算出、可拼出——无法静态枚举发送集；
- `load()` / `string.dump` 可运行时造代码——程序行为不可穷尽；
- metatable `__index` / 换 `_ENV` 可劫持名字解析——"闭集宿主函数表"这一前提不成立；
- 字符串与数字可互转——id 与信号名都能从文本长出来。

要保住静态可判定，就得把这些一条条禁掉；那时得到的是"被阉割到只剩现有表达力的 Lua"，代价是多一个引擎 + 一套沙箱 + 一堆限制规则，**表达能力却没有任何提高**。纯赔。

### 现有语言恰好能做到这件事（三条结构性原因）

不是"虽然简单但凑合"，而是**极简是可判定性的必要条件**：

1. **宿主函数表是编译期闭集。** `HOST_FNS` 编译期解析为 `CallHost`（`src/script/mod.rs:239-279`），无动态派发、无 eval——效果面从语法树即可枚举。
2. **关键标识符全是字面量。** `set_timer("resp", 200)` 的定时器名、`sig(0x100, "RPM")` 的信号名、`emit_value("名", ...)` 的派生名都是字面量，于是"哪个 handler 武装了哪个定时器、哪个定时器回了哪个报文"这条**响应映射**可由数据流纯静态推导。通用语言里定时器名通常是变量，推导当场断掉。
3. **id 的来源是封闭的。** 可能产生 id 的出口只有三处：字面量、常量算术、`frame_id()`。前两者落在常量/区间/已知集合域；第三者的取值范围恰好被 `on message <id>` / `on message *` 的事件绑定约束住。因此**发送集有限可枚举**——这就是编译期判定成立的根本原因。

此外，这个方向**已经在路上**：`TODO.md` P0 切片 3 已把"符号引用校验"定为红线，并明确校验位置在**装配层**、语言内核保持零总线假设。从"校验信号名"扩展到"校验报文发送集"是同一机制的增量延伸，现有先例见 `src/script/compiler.rs:550-572`（编译期收集 `signal_refs`）+ Apply 层对照 DBC 校验。

### 必须先立的语言规则（fail-closed）

**`send` / `send_ext` 的第一个参数必须静态可推导**（字面量、静态全局的有界算术、或 `frame_id()`）。出现 `send(sig(...))` 这类不可推导的 id 一律**编译报错**，而不是运行时兜底。同理，`set_timer` / `emit_value` 的名字也必须可推导。

这条规则与 `TODO.md` 既有的"拼错信号名是显式失败，不是运行时静默"是同一条纪律。**立这条规则等于永久拒绝一整类机制**（从文件/网络读 id 等），这是该定位的应有代价，要在语言设计上明确接受。

### 要做的静态分析

编译器侧多产出一份静态事实表，装配/Apply 层（与现有 `signal_refs` 校验同一处）拿 DBC 交叉核对，`--check-script` 复用同一路径直接做 CI 门禁。

| 静态推导 | 拿什么核对 | 报什么 |
| --- | --- | --- |
| 发送集：可能发出的 `(id, ext)` | DBC 的报文发送者声明 | 发了他节点 / 未声明的报文 |
| 响应映射：`on A` → 经哪个定时器 → `send B` | 发送集 + 事件绑定 + 定时器字面量名 | 应答了什么、延迟多久，可打印成一张表 |
| 写入集：`set_sig` 改了哪些 `(id, signal)` | DBC 信号归属 | 改了别人的信号 |
| 派生信号名集 | 会话命名空间（上限 256，`src/bus.rs:52-56`） | 重名 / 溢出 |
| 接收集：handler 声明的 id 集合 | DBC 声明 | 监听了他人的报文（合法但应可知） |
| 反向检查：DBC 声明本节点该发、脚本从不发 | 同上 | 漏实现（有独立价值） |

**已知难点：`on message *` 的通配转发**是唯一不可枚举的情形。不要当漏洞回避，而是归类为一个显式声明的角色——"本节点是转发者，发送集 = 接收集 ∩ 库声明"，并在报告里如实标注（顺便提示自激成环的风险，`docs/usage.md` 已有此警告）。

**运行时兜底（纵深防御，成本近乎为零）**：发送时查编译期算好的发送位图，越界则丢帧并记告警。编译期为主、运行时兜底，两头都不静默。

### 可以放心加的表达力 / 不能碰的红线

可以加（不破坏可推导性）：

- **有界定长数组 + 常量上界的循环**——补上最缺的"数组"，带界索引域分析起来毫无压力（嵌入式/安全关键 DSL 的标准做法）。**最推荐补这一项。**
- `switch` / `case`、复合赋值、位运算符：纯语法糖，对分析零影响。
- 日志用的字符串拼接已具备。

红线一句话：**每次给语言加特性前，先问"这会不会让效果集合变得不可静态推导"。**

### 外部仿真元件是另一回事

电池模型、诊断栈、被控对象仿真这类**宿主侧扩展**该走既有的 `register_extern` 注册缝（`src/script/mod.rs:302-311`，目前仅测试调用；解析顺序 registry → 节点钩子见 `src/script/vm.rs:381-392`），长期答案是有沙箱的多语言方案（WASM）。

**两件事不要混**：节点脚本要的是可分析，外部元件要的是可扩展，目标相反，必须用两套机制。也不要把裸 DLL 当答案（ABI 崩溃风险）。

## 5. 已否决的方向（不要重新提议）

| 方向 | 否决理由 |
| --- | --- |
| 换 Lua / JS / Python 作节点脚本底座 | 与"编译期可判定"正面冲突；得到的是表达力不变的阉割版 + 更多代码（见第 4 节） |
| 面板设计器 / HMI 控件 | 属于 CANoe 的"重"，且需要 `on key` / 控件事件等一整套动态事件模型（现无，`src/node.rs:5` 明确 "there are no panels"） |
| 诊断栈（UDS / ODX / CDD / 刷写） | 边界外的独立产品面，不是"多一种总线"；`TODO.md` 已归入协议轮次 |
| 工业级测试报告（HTML / XML / PDF 模板） | 与"零配置出结论"冲突；CSV + CLI 退出码已够，判定框架（见下）另议 |
| 多机分布式测量、实时系统、时间同步 | 定位外；核心线程为普通 `std::thread`，空闲睡 10 ms |
| 用户 / 权限管理、国际化 | 当前受众不构成瓶颈；中文字体与 IME 已解决实际痛点 |
| LIN / FlexRay / 以太网 / MF4 | 协议维度，按定位另行立项 |

**注意**：以上是"当前定位下"的否决。若定位改变（例如转向台架/HIL 业务），面板与诊断需要重新评估——但那时也应是明确的重启决策，不是慢慢渗进来。

## 6. 待决策 / 需要举证的点

1. **静态分析的表达力边界要定。** id 允许用算术构造到什么程度（纯常量？静态全局的区间？循环变量的已知域？）。**建议先做一次 spike**：拿 `examples/` 六个示例 + 预期用户脚本，测静态可推导的覆盖率，再决定抽象域的大小。若覆盖率不足，优先补"有界数组"而不是放宽规则。
2. **离线模式的语义与内存/时间预算。** 全量装载 vs 按需扫描（Graphics 的区间扫描已是按需路线）——两条路线是并存还是择一；大文件的装载时间与常驻内存目标是多少。
3. **离线模式与回放模式的关系。** 二者是不是同一个东西的两种驱动（一个按墙钟、一个按需）？如果统一，`--replay` / `--convert` 的 CLI 语义要不要一起收敛。**这是本建议里最需要先想清楚的设计问题**，它决定第 3 节第 1 件事的接口形状。
4. **发送集与 DBC 声明冲突时谁是权威。** 沿用既有的"错配报错而非静默"（`TODO.md` P0 红线），但要明确"脚本发了 DBC 未声明为本节点发送的报文"是编译错误还是可配置告警——建议默认错误，允许显式豁免。
5. **判定框架的边界。** 从静态分析能自然长出一个门禁能力（"发送集符合 DBC 声明"作为一条测试断言）。要不要顺势做成"带判定结果的自动化测试单元"（`TODO.md` 节点体系里的远期项），还是保持在 `--check-script` 的范围内——取决于是否需要"跑完仿真再给结论"而不只是"编译期给结论"。
